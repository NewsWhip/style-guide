    Which one do I use?

    These are two directives, not one with two names. A nwTooltip is a description of the element it sits on - short supplementary text, opened by hover or keyboard focus, never focusable. A nwPopover is a disclosure the user opens - a small dialog that can hold formatted content, links and buttons, which takes focus and traps it while open.

    Pick by what the content is, not by the open event you want: every event and timing on either one can be rebound. A panel with a link in it is a nwPopover even if it looks like a tooltip. See the API tab for the full reasoning.

    Tooltips



    A tooltip opens on mouseenter and closes on mouseleave, after a default delay of 500ms. It also opens when its host is focused from the keyboard, which is the keyboard equivalent of hovering - so the host has to be something that can hold focus. Try tabbing to the buttons above.

    On a screen narrower than the breakpoint input (767px by default) there is no hover to open it, so it opens on tap instead and is dismissed by tapping elsewhere. It is still a tooltip - only its events change.

    Customising close events

    Although not common, there are times when we want a tooltip to show on a disabled item but not be dismissed on click (which is the default behaviour). This is largely because of our default delay of 500ms. If the user clicks the element to which the tooltip is attached before the 500ms passes they won't see the tooltip which is, more than likely, explaining why the element is disabled.

    We can achieve the desired behaviour by specifying the events we want to close the tooltip, using the closeEvents input.

    Popovers



    A popover opens and closes on click, with no delay. From the keyboard that means Enter or Space, which the browser already turns into a click on a button host - so there is nothing to add. Escape closes it, as does the close button and, when enabled, a click outside.

    Keyboard behaviour

    Opening a popover from its host moves focus into the panel, which is what announces it and lets long content be read at the user's own pace. Where the panel has something tabbable in it focus is trapped there until it closes, and then returns to the trigger. Where it has nothing tabbable there is nothing to trap, so tabbing out simply closes it and carries on from the trigger - a trap around inert content would hold focus on its own hidden anchor, which reads as focus disappearing.

    Open each of these with the keyboard and tab through it. Note that a popover opened programmatically - from the isOpen input or show() - never steals focus, only one the user opened from the host.

    API reference for tooltips and popovers

    Directives

    Two directives, each with its own selector. They share an abstract base internally - it holds positioning, events and lifecycle, while each subclass decides what the callout means to assistive technology - but the base is not part of the public API, so these two are all you import. Pick by what the content is, per the FAQ below.

    TooltipDirective

    Attaches a description of the host element to it: short supplementary text, opened by hover or focus.

    Selector: [nwTooltip]

    Exported as: nw-tooltip

    The content reaches assistive technology through the host's aria-describedby whether the tooltip is open or not, which matters because a screen reader user cannot hover to open it. A tooltip never takes focus, so anything in it that could be operated would be unreachable
    PopoverDirective

    Attaches a disclosure the user opens: a small dialog that can hold formatted content, links and buttons, toggled by clicking the host.

    Selector: [nwPopover]

    Exported as: nw-popover

    Exposed as role="dialog", named after its trigger and described by its own content. It announces itself by taking focus, which is trapped there until it closes - on Escape, on the close button, or on a click outside - and then returns to where it came from

    Troubleshooting

    My tooltip is not closing on scroll even though I've set [closeOnScroll]="true".

    If your tooltip is inside a scrollable container, that scrollable container needs to have the cdkScrollable directive attached.

    My tooltip is not repositioning on scroll.

    As above, if your tooltip is inside a scrollable container, that scrollable container needs to have the cdkScrollable directive attached.

    How do I tweak the position of the tooltip?

    You can supply a containerClass input which you can apply styles against.

    Which selector do I use, and what does it change?

    nwTooltip is a description of the element it sits on: a short piece of supplementary text. It is exposed through the host's aria-describedby, opens on hover or keyboard focus, never takes focus, and must not contain anything focusable.

    nwPopover is a disclosure the user opens: a panel that can hold formatted content, links and buttons. It is exposed as role="dialog", named after its trigger and described by its own content, and announces itself by taking focus - which is trapped there until it closes, at which point focus returns to the trigger.

    Both are dismissed with the Escape key. The selector is what decides all of this, so pick it by what the content is, not by the default event you want - every event and timing on either one can be rebound. A panel with a link in it is a nwPopover even if it looks like a tooltip.

    They are separate directives, so the inputs are not interchangeable: withClose and closeOnOutsideClick exist on nwPopover only, and withAriaDescription, showOnFocus and breakpoint on nwTooltip only. Binding one on the wrong host is a template error rather than a silent no-op.

    What do I need to do to make the content available to screen readers?

    Nothing - the directive does it. Do not copy the content into an aria-label on the host element: it would be announced twice, and the two copies drift apart over time. Use aria-label only where it names the control rather than describing it, e.g. an icon button, and set [withAriaDescription]="false" where the host is already labelled with the same text.

    My tooltip never appears for keyboard users. Why?

    A hover-opened tooltip also opens when its host is focused from the keyboard, but only an element that can hold focus can be focused. A tooltip on a span, div, i or svg element will never open for a keyboard user. If the host is a control, make it a button. If it is not - if the tooltip only repeats text that is already on screen - then the description the directive adds for screen readers is all that is needed.

    Do not reach for a keydown handler on Enter or Space. Those are the host control's own activation keys, and on a button the browser already turns them into a click, which is what opens a popover.

    How much content should a tooltip hold?

    A string should be one sentence of supplementary text. It is added to the accessibility tree permanently, so it is announced every time the host is focused - a paragraph there is read out in full to someone who only wanted to know what a button does, and some users switch descriptions off entirely. Never put anything essential in one.

    Anything longer, or anything with structure, belongs in a nwPopover, so that the user asks for it. A popover is not described in advance: opening it moves focus to the panel, which is what announces it and lets it be read at the user's own pace.
